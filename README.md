# semaphore-tests
Простенький проект с агентскими инструкциями для создания E2E-тестов для semaphore. 

Собирает семафор из исходников, поднимает сервер и прогоняет тесты используя `playwright` и `pytest`. Содержит набор утилит для сброса базы, сессий браузера, и других мелких инструментов.
 
## Установка
1. Клонируем или копируем семафор в папку `semaphore`: 
```
cd semaphore
git clone https://github.com/semaphoreui/semaphore .

```

2. Запускаем скрипт сборки, он скачает нужные бинарники под go и другие зависимости в `vendor`, (требуемая версия go задаётся в env `GO_VERSION`):
```
./scripts/mac/build-semaphore.sh
./scripts/linux/build-semaphore.sh
```
Или напрямую (Node.js и curl должны быть установлены):
```bash
./scripts/build.sh            # собрать
./scripts/build.sh --verify   # собрать и проверить что сервер стартует
```

3. Устанавливаем uv и зависимости проекта (uv установится автоматически при первом запуске тестов или сервера, но можно вручную):
```
curl -LsSf https://astral.sh/uv/install.sh | sh
uv sync
uv run playwright install chromium
```

## Настройка тестов
Просто скопируй `env.example` как `.env`

### Сервер и порт, доступы
```dotenv
# Выдели отдельный порт чтобы не пересекался с сервером разработки 
SEMAPHORE_TEST_PORT=3100
SEMAPHORE_TEST_HOST=localhost
SEMAPHORE_TEST_ADMIN_USER=admin
SEMAPHORE_TEST_ADMIN_PASS=admin123
SEMAPHORE_TEST_ADMIN_EMAIL=admin@test.local
```
### Настройка тестов
```dotenv
# Максимум паралельных тестов, сейчас не применяется т.к. текущие тесты очищают базу. 
# Потребуется когда пойдут тесты использующие seeds 
SEMAPHORE_TEST_WORKERS=4
# Нужно-ли отображать браузер при работе (для отладки)
SEMAPHORE_TEST_HEADED=false
# Задержка при выполнении операций в браузере (замедляет тест чтобы увидеть что происходит) 
SEMAPHORE_TEST_SLOWMO=0
# Пауза перед закрытием браузера при завершении теста
SEMAPHORE_TEST_PAUSE=0
```
### Зависимости семафора:
```dotenv
# Версия go, должна совпадать с указанной в семафоре
GO_VERSION=1.24
```

## Запуск тестов
```
./scripts/mac/test.sh
./scripts/linux/test.sh
```

Или напрямую через uv:
```bash
uv run pytest tests/                        # все тесты
uv run pytest tests/test_01_auth.py         # один файл
uv run pytest tests/ -k test_login          # по имени
uv run pytest tests/ --headed               # с видимым браузером
```

## Просто поднять сервер
```
./scripts/mac/serve.sh
./scripts/linux/serve.sh
```

## Как с этим работать
1. Просим `claude` поднять сервер и открыть его в браузере
2. Объясняем что именно мы хотим проверить, просим изучить интерфейс и составить план теста
3. claude создаст тест по текущим инструкциям и сохранит информацию о нём в [`TESTS.md`](TESTS.md)

Полный индекс всех тестов и что именно они проверяют — в [`TESTS.md`](TESTS.md). Claude обновляет его автоматически при добавлении или удалении тестов.

### Что держим в голове
- Активный тестовый сервер один и база тестовая в этой конфигурации одна
- У тестов есть метки с указаниями, что именно нужно сделать перед тестом. Можно очистить базу или запустить seed который добавит нужные нам данные
- Лучше избегать параллельных тестов и гонять всё последовательно в тестах связанных с авторизацией, сессии могут пересекаться
- Если мы проверяем функциональную часть или добавление чего-то, можно сгруппировать такие тесты и гонять параллельно

### Если у нас сильно переписывается фронт
- В инструкциях прописано, что все селекторы тестов создаются константами в `src/pages`, достаточно будет обновить все файлы внутри

### Метки тестов
Метки (`pytest.mark`) управляют состоянием базы и сервера перед запуском теста. Выбирай наименее деструктивную: `parallel` > `seeded` > `clean_db`.

- `@clean_db` — сброс базы перед тестом, для деструктивных операций
- `@seeded(seed="name")` — заполняет базу данными через seed-функцию
- `@parallel` — тест не меняет данные, можно гонять параллельно
- `@clean_browser` — очищает куки без перезапуска сервера
