# semaphore-tests
Простенький проект с агентскими инструкциями для создания E2E-тестов для semaphore. 
- Агенту доступны инструменты для анализа SQLite-базы и клиент для создания тестовых данных через API семафора (для seed-генераторов тестов).
- Собирает семафор из исходников, поднимает сервер и прогоняет тесты используя `playwright` и `pytest`.
- Содержит набор утилит для сброса базы, сессий браузера, и генераторов данных для тестов.  
 
 
## Установка
1. Клонируем репозиторий
2. Клонируем или копируем семафор в папку `semaphore`: 
```
git clone https://github.com/semaphoreui/semaphore semaphore
```
3. Собираем семафор и проверяем что сервер стартует
```bash
./scripts/build.sh --verify
```
4. Устанавливаем окружение (uv, зависимости, Playwright):
```bash
./scripts/setup.sh
```
Или вручную:
```
curl -LsSf https://astral.sh/uv/install.sh | sh
uv sync
uv run playwright install chromium          # macOS
uv run playwright install --with-deps chromium  # Linux (ставит системные библиотеки)
```

## Настройка тестов
Копируем `env.example` как `.env`

### Сервер и порт, доступы
```dotenv
# Выдели отдельный порт чтобы не пересекался с сервером разработки 
SEMAPHORE_TEST_PORT=3100
SEMAPHORE_TEST_HOST=localhost
SEMAPHORE_TEST_ADMIN_USER=admin
SEMAPHORE_TEST_ADMIN_PASS=admin123
SEMAPHORE_TEST_ADMIN_EMAIL=admin@test.local
```
### Настройка тестов
Особое внимание `SEMAPHORE_TEST_HEADED=false`, мы не будем видеть что реально происходит в браузере.
```dotenv
# Максимум паралельных тестов, сейчас не применяется т.к. текущие тесты очищают базу. 
# Потребуется когда пойдут тесты использующие seeds 
SEMAPHORE_TEST_WORKERS=4
# Нужно-ли отображать браузер при работе (для отладки)
SEMAPHORE_TEST_HEADED=false
# Задержка при выполнении операций в браузере (замедляет тест чтобы увидеть что происходит) 
SEMAPHORE_TEST_SLOWMO=0
# Пауза перед закрытием браузера при завершении теста
SEMAPHORE_TEST_PAUSE=0
```
### Зависимости семафора:
```dotenv
# Версия go, должна совпадать с указанной в семафоре
GO_VERSION=1.24
```

## Список команд
Для сборки проекта
```bash
./scripts/setup.sh              # одноразовая установка окружения
./scripts/build.sh              # собрать семафор из исходников
./scripts/build.sh --verify     # собрать и проверить что сервер стартует
```

Если что-то идёт не так
```bash
./scripts/kill.sh               # убить все процессы семафора
```

Запуск тестов или отдельного теста
```bash
./scripts/test.sh               # запустить все тесты (headed)
./scripts/test.sh -k test_login # запустить по имени
```

Поднять сервер и открыть в обычном браузере:
```bash
./scripts/serve.sh                       # поднять сервер + открыть браузер
./scripts/serve.sh --seed empty_project  # очистить базу, применить seed, открыть браузер
```

Прямые команды (без скриптов):
```bash
uv run pytest tests/                        # все тесты
uv run pytest tests/test_01_auth.py         # один файл
uv run pytest tests/ -k test_login          # по имени
uv run pytest tests/ --headed               # с видимым браузером
```

## Как с этим работать
1. Просим `Claude` поднять сервер и открыть его в браузере
2. Объясняем что именно мы хотим проверить, просим изучить интерфейс и составить план теста
3. Если для теста потребуются тестовые данные, у агента есть набор инструментов для работы с базой `tool_db.py` и клиент `HTTP API` для добавления данных. Это позволит агенту создать `seed` данных для теста
4. Claude создаст тест по текущим инструкциям и сохранит информацию о нём в [`TESTS.md`](TESTS.md)

В целом, даже если для теста нужна нестандартная инфраструктура (поднять docker-контейнер, развернуть mock-сервис, сгенерировать SSH-ключи) — агент может это сделать самостоятельно, главное заложи стандарт как именно это должно происходить.

### Что держим в голове
- Тестовый сервер один и база в этой конфигурации одна
- У тестов есть метки с указаниями, что именно нужно сделать перед тестом (очистить базу, очистить сессию браузера, запустить seed)
- Типовой паттерн гонять тесты в однопоточном режиме и не беспокоится о состоянии базы
- Если тестов станет слишком много, часть тестов можно пускать параллельно (смотри метки ниже)

### Seeds и инструменты агента
- `src/seeds/api.py` — HTTP-клиент для Semaphore API. Позволяет агенту создавать записи во всех основных сущностях: проекты, ключи доступа, репозитории, инвентарь, окружения, шаблоны, views, расписания, задачи
- `tool_db.py` — инструмент для просмотра и снятия дампов с тестовой SQLite-базы (таблицы, схема, запросы, дампы отдельных таблиц)
- Seed-функции живут в `src/seeds/` — каждая это модуль с `run(base_url)`, который наполняет базу через API

Когда нужен тест с предзаполненными данными, агент создаёт seed-модуль и использует маркер `@seeded(seed="name")`.

### Если у нас сильно переписывается фронт
- В инструкциях прописано, что все селекторы тестов создаются константами в `src/pages`, достаточно будет обновить все файлы внутри

### Метки тестов
Метки (`pytest.mark`) управляют состоянием базы и сервера перед запуском теста. Выбирай наименее деструктивную: `parallel` > `seeded` > `clean_db`.

- `@clean_db` — сброс базы перед тестом, для деструктивных операций
- `@seeded(seed="name")` — заполняет базу данными через seed-функцию
- `@parallel` — тест не меняет данные, можно гонять параллельно
- `@clean_browser` — очищает куки без перезапуска сервера
